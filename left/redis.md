## 哈希表

哈希表其实就是一个数组，哈希桶存放的是指向键值对数据的指针，键值对数据结构里存放了 void * key 和 void * value 指针指向的是 Redis 对象（type,encoding,ptr）。ptr，指向底层数据结构的指针。键值对数据结构里还有next指针，将多个哈希值相同的键值对链接起来。

rehash：给「哈希表 2」 分配空间，一般会比「哈希表 1」 大一倍；将「哈希表 1 」的数据迁移到「哈希表 2」 中，「哈希表 1 」的空间会被释放，并把「哈希表 2」 设置为「哈希表 1」，然后在「哈希表 2」 新创建一个空白的哈希表

渐进式rehash：在 rehash 进行期间，每次哈希表元素进行新增、删除、查找或者更新操作时，Redis 除了会执行对应的操作之外，还会顺序将「哈希表 1 」中索引位置上的所有 key-value 迁移到「哈希表 2」 上

新增一个 key-value 时，会被保存到「哈希表 2 」里面，查找一个 key 的值的话，先会在「哈希表 1」 里面进行查找，如果没找到，就会继续到哈希表 2 里面进行找到。

根据负载因子触发rehash

当 Redis 缓存数据量大到一台服务器无法缓存时，就需要使用 Redis 切片集群。Redis Cluster 方案采用哈希槽（Hash Slot），每个键值对都会根据它的 key，被映射到一个哈希槽中，哈希槽被映射到具体的 Redis 节点上。

## 跳表

支持平均 O(logN) 复杂度的节点查找。「多层」的有序链表。插入节点随机设置一个层数


跨度实际上是为了计算这个节点在跳表中的排位。从头节点点到该结点的查询路径上，将沿途访问过的所有层的跨度累加起来，得到的结果就是目标节点在跳表中的排位。

如果当前节点的权重「小于」要查找的权重时，跳表就会访问该层上的下一个节点。

如果当前节点的权重「等于」要查找的权重时，并且当前节点的 SDS 类型数据「小于」要查找的数据时，跳表就会访问该层上的下一个节点。

如果上面两个条件都不满足，或者下一个节点为空时，跳表就会使用目前遍历到的节点的 level 数组里的下一层指针

平均每个节点包含 1.33 个指针，比平衡树更有优势。在做范围查找的时候，跳表比平衡树操作要简单。从算法实现难度上来比较，跳表比平衡树要简单得多。

（unlink）关闭文件、AOF 刷盘（everysec）、释放内存这三个任务都有各自的任务队列和后台线程

# AOF

AOF 日志：每执行一条写操作命令，就把该命令以追加的方式写入到一个文件里。将命令写入到日志的这个操作也是在主进程完成的

命令追加到server.aof_buf 缓冲区；通过 write() 系统调用，拷贝到了内核缓冲区 page cache；内核写入到硬盘

调用 fsync() 函数，这样内核就会将内核缓冲区的数据直接写入到硬盘

同步写回磁盘（立刻执行fsync）；（everysec）每秒写回磁盘（每秒执行）；OS决定（不执行）

Redis 为了避免 AOF 文件越写越大，提供了 AOF 重写机制。将当前数据库每一个键值对用一条命令记录到「新的 AOF 文件」。

重写 AOF 过程是由后台子进程 bgrewriteaof 来完成的。避免加锁。父子进程是共享内存数据的（物理空间），修改了该共享内存，就会发生「写时复制」。

当 Redis 执行完一个写命令之后，它会同时将这个写命令写入到 「AOF 缓冲区」和 「AOF 重写缓冲区」。当子进程完成 AOF 重写工作，会向主进程发送一条信号，主进程将 AOF 重写缓冲区中的所有内容追加到新的 AOF 的文件中。

复制父进程的页表，拷贝物理内存会导致阻塞父进程

# RDB

用 AOF 日志的方式来恢复数据其实是很慢的

RDB 快照：将某一时刻的内存数据，以二进制的方式写入磁盘；

执行了 save 命令，就会在主线程生成 RDB 文件；执行了 bgsave 命令，会创建一个子进程来生成 RDB 文件

RDB 文件的加载工作是在服务器启动时自动执行的，执行快照是一个比较重的操作，执行频率应比AOF低

bgsave 快照过程中，如果主线程修改了共享数据，发生了写时复制后，RDB 快照保存的是原本的内存数据，而主线程刚修改的数据，是没办法在这一时间写入 RDB 文件的

混合持久化工作在 AOF 日志重写过程。重写子进程会先将与主线程共享的内存数据以 RDB 方式写入到 AOF 文件，重写缓冲区里的增量命令会以 AOF 方式写入到 AOF 文件

# 过期淘汰

「过期字典」保存了数据库中所有 key 的过期时间。过期字典的 value 是一个 long long 类型的整数，这个整数保存了 key 的过期时间。字典实际上是哈希表

定时删除策略的做法是，在设置 key 的过期时间时，同时创建一个定时事件，当时间到达时，由事件处理器自动执行 key 的删除操作。对 CPU 不友好。

惰性删除策略的做法是，不主动删除过期键，每次从数据库访问 key 时，都检测 key 是否过期，如果过期则删除该 key。对内存不友好。

定期删除策略的做法是，每隔一段时间「随机」从数据库中取出一定数量的 key 进行检查，并删除其中的过期key。

Redis 选择「惰性删除+定期删除」这两种策略配和使用

当我们查询一个 key 时，Redis 首先检查该 key 是否存在于过期字典中。

定期删除：「已过期 key 的数量」占比「随机抽取 key 的数量」大于 25%，则继续抽查

# 内存淘汰

只有在 Redis 的运行内存达到了我们设置的最大运行内存，才会触发内存淘汰策略。

「在设置了过期时间的数据中进行淘汰」和「在所有数据范围内进行淘汰」这两类策略，每一类又可以细分为

随机淘汰

lru: 在 Redis 的对象结构体中添加一个额外的字段，用于记录此数据的最后一次访问时间。随机取 5 个值（此值可配置），然后淘汰最久没有使用的那个。

存在缓存污染问题，比如应用一次读取了大量的数据

在 LFU 算法中，Redis对象头的 24 bits 的 lru 字段被分成两段来存储，高 16bit 用来记录 key 的访问时间戳；低 8bit 用来记录 key 的访问频次。

在每次 key 被访问时，会先对 logc 做一个衰减操作，如果上一次访问的时间与这一次访问的时间差距很大，那么衰减的值就越大。对 logc 做完衰减操作后，就开始对 logc 进行增加操作，logc 越大的 key，它的 logc 就越难再增加。

# 主从复制

主服务器可以进行读写操作，当发生写操作时自动将写操作同步给从服务器，而从服务器一般是只读。

第一次同步（全量复制）：建立tcp长连接。主服务器传RDB文件给从服务器。主服务器将收到的写操作命令，写入到 replication buffer 缓冲区里。完成 RDB 的载入后，将 replication buffer 缓冲区里所记录的写操作命令发送给从服务器

主节点会给每个新连接的从节点，分配一个 replication buffer；当 replication buffer 满了，会导致连接断开，删除缓存，从节点重新连接，重新开始全量复制

从服务器可以有自己的从服务器，不仅可以接受主服务器同步的数据，也会把数据同步给自己旗下的从服务器

主从服务器间的网络连接断开，采用增量复制，把网络断开期间主服务器接收到的写操作命令，同步给从服务器。

在主服务器进行命令传播时，不仅会将写命令发送给从服务器，还会将写命令写入到环形缓冲区 repl_backlog_buffer

主服务器根据自己的 master_repl_offset 和 slave_repl_offset 之间的差距。如果判断出从服务器要读取的数据还在 repl_backlog_buffer 缓冲区里，增量复制

不存在 repl_backlog_buffer 缓冲区里，那么主服务器将采用全量同步的方式。

Redis 从节点每隔 1 秒发送 replconf ack{offset} 命令，实时监测主从节点网络状态；检查复制数据是否丢失。

删除或淘汰一个key，del命令发送给从节点

脑裂：主与所有的从节点都失联了，哨兵发现主节点失联了，哨兵就会在「从节点」中选举出一个 leader 作为主节点，这时集群就有两个主节点了，旧主节点会降级为从节点，数据丢失。

当主节点发现「从节点下线的数量太多」，或者「主从复制网络延迟太大」的时候，那么主节点会禁止写操作，直接把错误返回给客户端。

# 缓存更新

并发请求更新，无论是「先更新数据库，再更新缓存」，还是「先更新缓存，再更新数据库」，都可能出现缓存和数据库中的数据不一致的现象

## Cache Aside

写时不更新缓存，删除一个数据，相比更新一个数据更加轻量级

写：先更新数据库中的数据，再删除缓存中的数据。

先删除缓存，如果有并发读，可能出现不一致。先更新数据库，如果有并发读，缓存可能被更新为旧值，可能性很小

读：如果读取的数据没有命中缓存，则从数据库中读取数据，然后将数据写入到缓存，并且返回给用户

适合读多写少的场景，不适合写多的场景。经常没有缓存。在更新数据时也更新缓存，在更新缓存前先加一个分布式锁或者给缓存加一个较短的过期时间

不管是先操作数据库，还是先操作缓存，只要第二个操作失败都会出现数据一致的问题

将第二个操作（删除缓存）要操作的数据加入到消息队列。如果应用删除缓存失败，可以从消息队列中重新读取数据，然后再次删除缓存，如果删除缓存成功，就要把数据从消息队列中移除

通过订阅 binlog 日志，拿到具体要操作的数据，然后再执行缓存删除，再回 ack 机制给消息队列

## Read/Write Through

应用程序只和缓存交互，更新数据库的操作由缓存自己代理了

读：将结果写入到缓存组件

写：缓存中数据已经存在，则更新缓存中的数据；缓存中数据不存在，直接更新数据库

## write back

只更新缓存，同时将缓存数据设置为脏的，适合写多的场景，会有数据丢失的风险

将缓存失效时间随机打散。

如果发现访问的数据不在 Redis 里，就加个互斥锁，当缓存构建完成后，再释放锁。

后台线程负责频繁地检测缓存是否有效，马上从数据库读取数据，并更新到缓存

业务线程发现缓存数据失效后（缓存数据被淘汰），通过消息队列发送一条消息通知后台线程更新缓存

暂停业务应用对缓存服务的访问，只将少部分请求发送到数据库进行处理

主从节点的方式构建 Redis 缓存高可靠集群。

## 缓存穿透

当用户访问的数据，既不在缓存中，也不在数据库中。

非法请求的限制。在缓存中设置一个空值或者默认值。查询布隆过滤器快速判断数据是否存在数据库。当我们在写入数据库数据时，在布隆过滤器里做个标记

使用 N 个哈希函数分别对数据做哈希计算，N 个哈希值对位图数组的长度取模，将每个哈希值在位图数组的对应位置的值设置为 1；

查询布隆过滤器说数据存在，并不一定证明数据库中存在这个数据。查询到数据不存在，数据库中一定就不存在这个数据。

热点数据动态缓存的策略总体思路：通过数据最新访问时间来做排名，并过滤掉不常访问的数据，只留下经常访问的数据。
